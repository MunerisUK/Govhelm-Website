The architecture pack

Fourteen documents, from government functions to deployment

Written as a Layer 0–1 enterprise architecture framework for a government deciding how to hold citizen data, and published alongside the platform that implements it. The jurisdiction profiles the documents publish are the same files the platform loads.

#DocumentWhat it covers
01Government functions (top 20)The highest-volume government functions and the citizen data each consumes.
02Architecture principlesThe non-negotiables, led by “collect once, never duplicate”.
03Reference architectureThe layered target architecture, the system-of-record map and the integration patterns.
04Single Citizen Record & data domainsMaster data, authoritative sources, the resolver and the no-duplication mechanism.
05Digitally-enabled policy agreementsPolicy-as-code: how a legal data-sharing agreement becomes an enforced runtime control.
06Platform build on SAP + Microsoft AzureThe concrete technology mapping, including where ERP and citizen data stay in their lanes.
07Delivery roadmap & operating modelPhasing, governance, risks and the team to run it.
08Target Operating ModelFrom siloed departments to a federated model on a shared spine.
09Breaking the silos — a playbookRoot causes, the seven levers, the tactical plays and a sequenced action list.
10TOGAF-based capabilitiesThe business capability model, the BDAT domains and the ADM mapped to the roadmap.
11Appendix A — departmental structureThe verified department list and department → data-domain ownership.
12Appendix B — UK structure & comparisonThe UK ministerial departments mapped onto a small jurisdiction’s consolidated set.
13Government-as-a-ServiceCommon Core versus Jurisdiction Profile, and the commonality and variability analysis behind it.
14Deployment & deliveryOne image, per-jurisdiction tenancies, GitOps promotion and the rollback story.

Decision record

Fourteen decisions, served live by the running system

The authenticated admin architecture view serves these from the deployment itself, so what an assessor reads is what the deployment is running — not a document that drifted from it two releases ago.

#DecisionIn one line
ADR-0001Profile-driven multi-tenancyEvery jurisdictional difference is a value read from a profile, never a branch in the code.
ADR-0002Single Citizen Record — thin master with pointersThe master holds minimal identity attributes and pointers to systems of record. Detail stays where it is owned.
ADR-0003In-process event backbone for cross-capability reactionsA producer publishes a fact carrying a reference and does not know who consumes it.
ADR-0004Server-side rendering, no client frameworkPages are rendered on the server, so the service works without JavaScript and the accessibility surface stays small.
ADR-0005Policy-gated data minimisationCross-domain reads return derived claims, checked against an agreement, with allow and deny both audited.
ADR-0006Deployment & deliveryOne image, one isolated tenancy per government, config-only differences, GitOps promotion.
ADR-0007Persistence — repository seam with a Postgres backendThe domain logic runs unchanged over the in-memory store or Postgres; storage is behind a seam.
ADR-0008Data-sharing agreements are per-jurisdiction configurationA tenant declares its own agreement register, or inherits the platform baseline.
ADR-0009Outbound integrations are governed data-product publishersAn export is policy-gated and audited exactly like an in-app read.
ADR-0010Finance / ERP integrationGoverned claims in, instructions out — the platform never holds the ledger.
ADR-0011HR / Payroll integrationGoverned employment claims in, leaver instructions out.
ADR-0012Adopt TypeScript incrementallyNew modules are born typed and run under Node’s type stripping; the existing core calls in unchanged.
ADR-0013Open-data (DCAT) transparency layerThe rules that gate access to citizen data are published as open data; the data itself never is.
ADR-0014Identity resolver (EMPI)Identifier cross-reference plus a governed resolve(): looking someone up is an access, and is audited as one.

Reference

The rest of the documentation

The platform repository carries its own documentation next to the code it describes: the Common Core guide, the jurisdiction profile schema with the committed reference profiles, the deployment layer with the chart and the promotion model, and the integration definitions for partner systems of record.

Two market documents are also published: a competitive landscape with the confidence of every figure flagged, and a positioning one-pager. They are working drafts for discussion rather than approved communications, and they say so at the top.

Also published

  • The Common Core guide and the runnable reference build
  • The jurisdiction profile schema and eight reference profiles
  • The deployment layer: chart, tenant descriptors, promotion guard
  • The CivitaOS integration definition and its conformance checklist
  • Competitive landscape and positioning, with confidence flagged

Documentation is versioned with the platform. Where a document and the code disagree, the code is the contract — and the disagreement is a bug in the document.
