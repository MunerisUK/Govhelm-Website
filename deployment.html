Deployment

One image. One isolated deployment per government. Config-only differences, and promotion by changing a single pinned digest that has already been proven in that government’s own test ring.

Talk to us about hostingSecurity & data

  • One image for every tenant
  • One database per tenant
  • Rollback is reverting a pin

The model

Central build produces one image. Every government runs that image with its own tenant descriptor: the tenant id, the public host, the data-residency region, the replica count and an immutable image digest. That descriptor is the entire surface that varies between governments.

A pod serves exactly one tenant, pinned by environment. Multi-tenant routing exists for evaluation and reference environments; in service, isolation is a deployment boundary, not a path prefix or a query filter.

The chart

The chart is tenant-agnostic: no jurisdiction appears in any template. It sets the tenant, pins the image by digest rather than by a mutable tag, wires liveness and readiness probes, applies a default-deny network policy that admits only the ingress controller, and creates a per-tenant ingress host.

Promotion

Central CI builds one image and pins its digest into every test descriptor automatically. Each test ring syncs and runs its own smoke and contract tests. A move to production is a pull request, owned and approved by that government, that bumps one line — and a promotion guard refuses a production digest that has not been proven in that same government’s test ring.

Governments promote independently, so two may sit on different production builds at the same time. That is intended: the single image runs any valid profile, so a jurisdiction is never forced to take a release on somebody else’s schedule. Rollback is reverting the pin.

Data

Durable persistence is Postgres, one database per government. The connection string comes from an existing secret provisioned per environment, never from a chart value and never from a profile. Migrations run as a pre-sync job before the application starts, so a release never serves traffic against a schema it has not migrated.

Without a database configured the platform runs on its in-memory backend. That is right for a demonstration or an evaluation environment and wrong for everything else, and the documentation says so rather than leaving it to be discovered.

Operating it

Small jurisdictions are small: the reference resource requests are modest and the production descriptors run two to three replicas. Scale is a descriptor edit. The interesting operational question in this architecture is rarely capacity — it is residency, key custody and who is able to approve a promotion.

The promotion model

central CI builds ONE image
   -> pins the digest into every tenants/*/test        (automatic)
   -> Argo CD syncs each test ring
   -> per-tenant smoke and contract tests
   -> [government] PR bumps tenants/<gov>/prod digest  (approved)
        guarded: a prod digest must be test-proven for THAT tenant
   -> Argo CD syncs that government's production
   -> rollback = revert the pin

Why a digest and not a tag

The pin is the whole change

A mutable tag means the artefact a government approved is not necessarily the artefact it runs. Pinning an immutable digest makes the promotion auditable: one line, one reviewer, one artefact, and a git history that says exactly which build each government was running on any given day.

It also makes rollback trivial and boring, which is the property you want at two in the morning. Revert the commit; the previous digest is still there.

The guard is the part that matters for assurance: a production descriptor may only run a digest already proven in that tenant’s own test ring. Another government’s successful test does not count.

The tenant descriptor

Everything that varies between two governments, deployed

The jurisdiction profile carries what a government is. The tenant descriptor carries where it runs. Between them there is nothing else to configure.

deploy/tenants/<government>/prod/values.yaml

# The digest here changes ONLY by a government-owned, approved
# promotion of a build already proven in that government's test ring.
tenant: jersey
host: gov.je
region: eu-jsy-1
replicaCount: 3
image:
  repository: registry.example.gov/gaas
  digest: "sha256:1111…"

What the chart guarantees

  • No jurisdiction name in any template
  • The image pinned by digest, never by a mutable tag
  • Liveness and readiness probes, readiness covering the database
  • Default-deny network policy; ingress only from the ingress controller
  • A migration job that runs before the application starts
  • One database per government, from a secret provisioned per environment

Repository layout

Environment state lives apart from application code

In production the per-tenant descriptors belong in a separate environment repository, so application code and environment state have independent histories and independent access control. A government approving a promotion should not need write access to the platform source, and a platform engineer should not be able to move a government to production alone.

Reference descriptors are committed alongside the chart as runnable, reviewable examples — including a deliberate skew between two governments on different production builds, because that is the normal state of a healthy multi-tenant estate, not a fault to be corrected.

Continuous delivery

  • Build on a version tag, or by manual dispatch — not on every commit
  • Digest pinned into every test descriptor automatically
  • Promotion is a manual dispatch, per tenant and environment
  • The promotion guard runs before any production digest changes

The publishing workflows are templates: they need a container registry and credentials you provide, and deliberately do not run on ordinary commits.
