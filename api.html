API reference

Every citizen-facing route is tenant-scoped. There is no route that spans tenants, and no parameter that widens one — isolation is in the shape of the URL space as well as in the database.

Request evaluation accessDeployment guide

Conventions

Citizen-facing routes live under /t/:tenant/. The tenant segment selects the jurisdiction profile, and everything below it — the record, the agreements, the audit log, the logo — is scoped to that tenant only. An agreement in one tenancy can never authorise an access in another.

In a production deployment a pod serves exactly one tenant, pinned by the TENANT environment variable, so the multi-tenant routing above is for evaluation and reference environments. Isolation in service is a deployment boundary, not a path prefix.

Service pages are server-rendered HTML; the open-data endpoints return JSON-LD and JSON. Writes are form posts, because the portal works without JavaScript.

Transparency

Open data: the rules, never the record

Each tenant publishes the governance metadata that ought to be public: which consumer may read what, for which purpose, which exact fields, on what legal basis — and which capabilities the jurisdiction runs. It follows the W3C Data Catalog Vocabulary as JSON-LD, with the raw datasets offered as plain-JSON distributions.

Nothing personal is in this layer by construction. The citizen record, the claims, the income and the audit entries are deliberately absent. The minimisation guarantee that keeps the record closed is precisely what makes the metadata safe to open.

Government open data conventionally ships under an open government licence, and that is the default; a jurisdiction may override it in its profile.

GET /t/<tenant>/open-data/agreements.json

[
  {
    "id": "AGR-BEN-REV",
    "consumer": "benefits_service",
    "domain": "revenue.status",
    "purpose": "benefit_assessment",
    "fields": ["belowThreshold"],
    "legalBasis": "public_task"

The event backbone

// A producer publishes a fact carrying a REFERENCE, not a figure.
DeathRegistered  { tenant, personKey, occurredAt }
IncomeUpdated    { tenant, personKey, occurredAt }

// Subscribers registered in the wiring module react by reading the
// one record, by reference, under their own agreement:
//
//   DeathRegistered -> pension service    (AGR-DTH-PEN)
//                   -> electoral service  (AGR-DTH-ELE)
//                   -> payroll leaver instruction, where HR is configured
//   IncomeUpdated   -> benefits re-assessment (AGR-BEN-REV)
//
// Every reaction is policy-checked and lands in the citizen audit log.

Events

Two producers, several consumers, no coupling

The bus carries no tenant data. Handlers are jurisdiction-agnostic capability code and the tenant is passed at publish time, so one registration set serves every government and a handler only ever touches the tenant it was handed.

Subscribers are awaited in registration order rather than raced, so a fan-out is deterministic and the audit trail reads in the order things actually happened — which matters when somebody has to reconstruct a decision two years later.

Adding a consumer does not change the producer. That is the point: the service that registers a death does not know, and must not need to know, which other services care.

A jurisdiction inherits this baseline unless its profile declares its own. Note that two different consumers read the same revenue claim for two different purposes, and each needs its own agreement.

Raw income is in no agreement at all

There is no row here, and no row a jurisdiction can add through ordinary configuration, that returns the income figure to a consumer outside revenue. That is minimisation enforced by absence rather than by a rule somebody could relax.

Operations

Operational surface

Liveness and readiness endpoints back the container probes; readiness includes the persistence backend, so a tenancy whose database is unreachable does not take traffic.

Configuration is environment, not profile: the tenant to serve, the port, the database connection string, the administrator credentials and the session secret. Credentials never appear in a jurisdiction profile, because profiles are reviewable configuration in version control and secrets are not.

The status of this surface

This is a reference build. The routes are real and runnable, but the API is not yet versioned and is not covered by a stability commitment. Version and deprecation policy arrive with 1.0 — see the roadmap.
