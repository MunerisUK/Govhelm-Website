Platform

Twelve capabilities, and the extensions that are not universal

The catalogue is jurisdiction-agnostic and identical for every tenant. A profile does not define capabilities; it toggles which of them the government runs. Adding a capability is additive for everyone, gated on a capability id, and never on a jurisdiction name.

Wired end to end

The four that prove the architecture

These are not four separate applications. They are four capabilities composed on one record, one decision point and one event bus — which is the whole claim, made testable.

Register a birth, death or marriage — once.

Identity & Life Events

Wired end to end: the single citizen record, the policy decision point, the Tell Us Once fan-out and the citizen audit trail all run behind this one tile.

View and file your tax; see what you owe.

Revenue & Taxation

The write side. Revenue owns the income figure, so it alone sees the raw amount; filing publishes an event carrying a reference, never the number.

Check entitlement and apply for support.

Social Protection & Benefits

Composed on the same record with no store of its own. It reads the same means-test claim Identity reads, as a different consumer under a different purpose.

Manage appointments and access your care record.

Health & Care

Delivered through a deep integration to CommVita rather than natively. The platform never becomes the clinical system of record.

Toggles

A capability is on because a profile says so

The most expensive sentence in government software is “this jurisdiction is different, so we forked it”. A government that levies no personal income tax does not get a variant build here; it gets revenue_taxation: false and the customs and duties capability instead.

The toggle block is validated at load. A capability id the platform does not know is a startup error, not a silently ignored line, so a typo in a profile fails fast rather than quietly disabling a public service.

config/jurisdiction-profiles/<tenant>.yaml

capabilities:                             # feature toggles
  identity_life_events: true
  revenue_taxation: false                 # no personal income tax here
  indirect_revenue_customs: true          # so duties carry the revenue function
  social_protection_benefits: true
  health_and_care: true                   # delivered via the CommVita seam
  education_skills: true
  justice_public_safety: true
  borders_immigration: true
  housing_communities: true
  economy_business_regulation: true
  infrastructure_environment_transport: true
  civic_participation_elections: true
  parish_administration: false            # extension: not every government has parishes
  residential_qualification_control: false

Extensions

Capabilities that not every government has

Some jurisdictions run functions the rest do not. An extension ships in the single central image for everyone, registers like any other capability, and switches on only for the profiles whose toggles enable it. That is the country-specific module with zero fork.

parish_administration · Designed

Parish Administration

Parish-level civic administration: rates, parish enquiries and local services.

Ships in the single image for everyone and switches on only for the profiles whose toggles enable it.

residential_qualification_control · Designed

Residential Qualification Control

Residential and employment status that gates housing and work rights and changes with length of residency; distinct from nationality and immigration status.

The status categories and the governing law are profile data, so the module itself never names a jurisdiction.

Why an extension is not a fork

Both extensions are in the image every government runs. The concrete detail — how many parishes, which residential status categories, which governing law — is profile data, so the module itself never names a jurisdiction and the lint that forbids jurisdiction names in the core still passes.

Adding a capability

  • Register it in the catalogue with an id, a summary and a citizen-facing sentence
  • Give it a route when the service behind it is wired; until then it renders as a tile
  • Every tenant can now toggle it — no per-government work, no fork
  • If it is not universal, ship it as an extension instead; the rule is identical

Extensibility

The tenth government does not pay for the first

Because a capability enters the system in exactly one place and is gated on an id, building one for a jurisdiction that needs it makes it available to every jurisdiction that wants it. The work is done once and the toggle is free.

This is the structural reason the economics differ from a systems integrator’s. An SI is paid to build the same capability again for the next government, because the last one lives in a codebase only that government runs. Here it lives in the image everyone runs.

How a government is onboarded

Which capabilities would you switch on first?

Most jurisdictions start with one: life events and Tell Us Once, or a governed analytics data product. Land one capability, prove the governance, then open the toggles.
